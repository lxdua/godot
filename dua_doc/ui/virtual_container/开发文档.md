# VirtualBoxContainer 虚拟化容器控件 · 开发文档

> 目标：为 Godot 补齐 `BoxContainer` / `GridContainer` 的**虚拟化对位控件**——当同质子项规模达到几百到几万条时，只为视口内的条目实例化真实节点，其余按需回收复用。覆盖背包、聊天、排行榜、动态流、资源库等高频场景。
> 状态：设计草案 v0.2
> 归属：`scene/gui/virtual_box_container.cpp/h`（暂定）

---

## 1. 背景

### 1.1 问题陈述

`BoxContainer` / `GridContainer` / `FlowContainer` 家族要求所有子项都是**真实存在的 Control 节点**。当子项是自定义 `PackedScene`（带图标、按钮、动画、子控件）时，100 条物品 = 100 个完整节点树、100 份信号连接、100 次 `_ready`。

当数据规模达到几百到几万条（游戏背包、聊天记录、资源库、排行榜、物品选择器）时，这种做法：

* 内存占用线性增长
* `NOTIFICATION_SORT_CHILDREN` 级联触发，布局耗时显著
* 滚动时重绘全量区域（即便不可见）
* 首次打开面板出现明显掉帧

### 1.2 现状替代品的局限

| 控件 | 虚拟化 | 支持 PackedScene 作单元 | 结论 |
|---|---|---|---|
| `ItemList` | ✅（自绘） | ❌ | 功能受限，文本+图标以外做不了 |
| `Tree` | ✅（自绘） | ❌ | 同上，且 API 偏重数据树 |
| `BoxContainer` (V/H) + `ScrollContainer` | ❌ | ✅ | 朴素方案，规模上来就崩 |
| `GridContainer` | ❌ | ✅ | 同上 |
| `FlowContainer` | ❌ | ✅ | 同上 |
| 社区插件（Asset Library 多个 virtual-list） | ✅ | ✅ | 各自为政，覆盖面残缺 |

**关键缺口**：`BoxContainer` / `GridContainer` 家族**没有虚拟化对位**。这是 Godot UI 生态中最频繁被用户重复实现、也最容易实现错的一块。

### 1.3 目标

提供一个 `Container` 子类 `VirtualBoxContainer`（及其派生 `VirtualGridContainer`），做到：

1. 以一个（或多个）`PackedScene` 作为条目模板
2. 只为**当前视口可见条目 + 少量缓冲**实例化节点
3. 通过**节点回收池**在滚动时重用节点，避免频繁 `instantiate / free`
4. 用户只需关心数据模型与"数据 → 节点"的单向绑定
5. API 与 `BoxContainer` 家族保持心智对齐（`vertical` 属性、`item_*` 前缀属性）
6. 默认支持等高模式，预留可变高度扩展

### 1.4 非目标

* 不取代 `BoxContainer` / `GridContainer`（小规模或异构结构化布局仍用它们）
* 不取代 `ItemList` / `Tree`（它们的自绘路径仍更轻量）
* 不引入响应式数据系统（Observable / Reactive）
* 不实现树形 / 缩进（初版只做线性 / 网格布局，后续再出 `VirtualTree`）
* 不内建排序 / 筛选（由数据源负责）

### 1.5 何时用 BoxContainer，何时用 VirtualBoxContainer

这是用户最需要先厘清的决策点，必须在官方文档顶端醒目呈现：

| 场景 | 推荐 | 理由 |
|---|---|---|
| < 100 个同质子项 | `VBoxContainer` / `HBoxContainer` / `GridContainer` | 零迁移成本，虚拟化 bookkeeping 开销不值 |
| 100 ~ 1000 个同质子项 | 视实测帧率决定 | 复杂单元（带动画 / 渲染）越界早，简单单元可宽 |
| 1000+ 个同质子项 | **`VirtualBoxContainer` / `VirtualGridContainer`** | 节点数常数级，性能跟随视口而非总数 |
| 异构结构化布局（设置页、HUD、对话框） | `BoxContainer` 家族 | 虚拟化要求数据化，结构化 UI 不适合迁移 |
| 用户代码需要 `@onready var xxx = $Container/ChildX` 形式引用子节点 | `BoxContainer` 家族 | 虚拟化节点随时可能回收重建，引用会失效 |
| 子节点有独立生命周期（如拖拽系统从别处 `add_child` 进来） | `BoxContainer` 家族 | 虚拟化容器拥有节点所有权，不容忍外部生命周期 |

**核心判据**：子项能否由"数据 + 模板"完全重建？能 → 考虑 `VirtualBoxContainer`；不能 → 用 `BoxContainer`。

## 2. 设计原则

1. **数据在外，节点在内**：容器不持有数据，只持有"总条数 + 绑定回调"。数据变化由用户显式通知。
2. **节点是无状态展示层**：一切状态（选中、展开、编辑中的文本）存数据侧；节点可以随时被回收。
3. **单向数据流**：`data → bind_item → node`。反向脏状态通过 `unbind_item` 的提交时机回写。
4. **按类型分池**：混合类型单元通过 `type_provider` 区分；每种类型独立回收池，不跨类型复用。
5. **零魔法**：不 hook `Array`，不反射用户类型；所有数据变更必须显式调用 `refresh_*` / `notify_*`。
6. **API 心智对齐 `BoxContainer`**：`vertical` 属性、`separation` 主题项等与现有家族同名同义，降低迁移成本。

```
┌──────────────────────────────────────────────────────────┐
│                   VirtualBoxContainer                    │
│  (Container, 本质上是自管滚动 + 视口 + 节点回收的容器)    │

│   ┌────────────┐   ┌──────────────┐   ┌─────────────┐    │
│   │ Viewport   │   │  Recycler    │   │  Layouter   │    │
│   │ Window     │◀──│  (Pool Map)  │   │ (等高 / 自适) │    │
│   └────────────┘   └──────────────┘   └─────────────┘    │
│         ▲                 ▲                  ▲           │
│         │                 │                  │           │
│   滚动位置 / 尺寸    (type → pool)      item_count       │
│                                         item_min_size    │
│                                                          │
│   [活跃节点 active_nodes : Map<index, Node>]             │

派生:
```

### 3.1 核心数据结构

```cpp
class VirtualBoxContainer : public Container {
    GDCLASS(VirtualBoxContainer, Container);

    // --- 模板 ---
    Ref<PackedScene> item_scene;                  // 单模板
    Vector<Ref<PackedScene>> item_scenes;         // 多模板（混合类型）
    Callable type_provider;                       // (index:int) -> int

    // --- 数据规模 ---
    int item_count = 0;

    // --- 布局（对位 BoxContainer）---
    bool vertical = true;                         // 与 BoxContainer.vertical 一致
    enum SizeMode { FIXED_SIZE, VARIABLE_SIZE };
    SizeMode size_mode = FIXED_SIZE;
    Vector2 item_min_size = Vector2(0, 48);       // FIXED_SIZE 下单元尺寸
    int estimate_item_size = 48;                  // VARIABLE_SIZE 估算

    // --- 缓冲 ---
    int buffer_items = 2;                         // 视口前后各多几个

    // --- 运行时 ---
    double scroll_offset = 0.0;                   // 主轴偏移
    HashMap<int, Control *> active_nodes;         // index -> 节点
    HashMap<int, LocalVector<Control *>> pools;   // type -> 回收池
    HashMap<int, Vector2> measured_sizes;         // VARIABLE_SIZE 已测尺寸
};

class VirtualGridContainer : public VirtualBoxContainer {
    GDCLASS(VirtualGridContainer, VirtualBoxContainer);

    int columns = 1;                              // 对位 GridContainer.columns
};
```

### 3.2 节点生命周期

```
        未创建 (index 不在视口)
            │
            │ 进入视口
            ▼
     ┌────────────┐
     │ 从对应池取 │ 空则 instantiate()
     └─────┬──────┘
           │
           ▼
     发出 bind_item(node, index)  ← 用户用 data[index] 填充 node
           │
           ▼
     添加到 active_nodes，定位
           │
           │ 滚出视口
           ▼
     发出 unbind_item(node, index)  ← 用户把节点脏状态回写 data
           │
           ▼
     从 active_nodes 移除
           │
           ▼
     remove_child 并放回对应 type 的池
           │
           ▼
     达到池上限则 queue_free()
```

**关键点**：

* 回收时**不** `free` 节点，只 `remove_child`，节点保持在内存中等待复用
* 信号连接保留（用户可以在 `_ready` 里一次性连好，之后每次 `bind_item` 只更新数据）
* 池有上限（默认每种 type 32 个），防止内存无限增长

## 4. API 设计

### 4.1 属性

| 属性 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `item_scene` | `PackedScene` | `null` | 单模板；若设置，`item_scenes` 被忽略 |
| `item_scenes` | `Array[PackedScene]` | `[]` | 多模板数组，下标即 type |
| `type_provider` | `Callable` | `null` | `(index:int) -> int`；未设则所有条目 type=0 |
| `item_count` | `int` | `0` | 总条数；赋值触发 `refresh()` |
| `vertical` | `bool` | `true` | 主轴方向，对位 `BoxContainer.vertical` |
| `size_mode` | `int` (enum) | `FIXED_SIZE` | 等高或可变 |
| `item_min_size` | `Vector2` | `(0, 48)` | 等高模式下的单元尺寸 |
| `buffer_items` | `int` | `2` | 视口前后各预加载几个 |
| `pool_size_limit` | `int` | `32` | 每种 type 的池上限 |

**主题项**（继承 `Container`，以 `BoxContainer` / `GridContainer` 为对位）：

| 主题项 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `separation` | `int` | `4` | 相邻条目之间的间距（px），对位 `BoxContainer.separation` |
| `h_separation` | `int` | `4` | 仅 `VirtualGridContainer`：列间距，对位 `GridContainer.h_separation` |
| `v_separation` | `int` | `4` | 仅 `VirtualGridContainer`：行间距，对位 `GridContainer.v_separation` |

`VirtualGridContainer` 额外：

| 属性 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `columns` | `int` | `1` | 对位 `GridContainer.columns`；`vertical=true` 时为列数，`vertical=false` 时为行数 |

### 4.2 方法

### 4.4 典型用法

**背包（垂直列表，同质单元）：**

```gdscript
@onready var list: VirtualBoxContainer = $Inventory
var inventory: Array[ItemData] = []

func _ready() -> void:
    list.item_scene = preload("res://ui/inventory_slot.tscn")
    list.vertical = true
    list.item_min_size = Vector2(0, 64)
    list.bind_item.connect(_on_bind)
    list.item_activated.connect(_on_use)

    inventory = load_inventory()
    list.item_count = inventory.size()

func _on_bind(node: Control, index: int) -> void:
    node.set_data(inventory[index])

func _on_use(index: int) -> void:
    player.use_item(inventory[index])
    inventory.remove_at(index)
    list.notify_item_removed(index)
```

**聊天列表（垂直，混合单元）：**

```gdscript
list.item_scenes = [TEXT_MSG, IMAGE_MSG, SYSTEM_MSG]
list.type_provider = func(i: int) -> int:
    return messages[i].kind
list.bind_item.connect(func(node, i):
    node.fill(messages[i]))
list.item_count = messages.size()

# 来了一条新消息
messages.append(new_msg)
list.notify_item_inserted(messages.size() - 1)
list.scroll_to_index(messages.size() - 1, VirtualBoxContainer.ALIGN_END)
```

## 5. 关键算法

### 5.1 视口可见区间计算（FIXED_SIZE，线性）

**核心公式**：每个条目占据的主轴步进包含单元尺寸 + 间距：

```
item_size     = vertical ? item_min_size.y : item_min_size.x
separation    = theme_cache.separation
item_stride   = item_size + separation        # 相邻条目的主轴间距步长
viewport_ext  = vertical ? size.y : size.x

# 条目 i 的主轴起点：
pos(i) = i * item_stride

# 视口区间（含 buffer）：
first = max(0, floor(scroll_offset / item_stride) - buffer_items)
last  = min(item_count - 1,
            ceil((scroll_offset + viewport_ext) / item_stride) - 1 + buffer_items)
```

**总内容尺寸**：`total = item_count * item_stride - separation`（末尾条目后不再有间距；`item_count=0` 时为 0）。用于滚动条 `max`。

### 5.2 视口可见区间计算（网格，FIXED_SIZE）

```
row_size     = vertical ? item_min_size.y : item_min_size.x
col_size     = vertical ? item_min_size.x : item_min_size.y
v_sep        = theme_cache.v_separation
h_sep        = theme_cache.h_separation

row_stride   = row_size + v_sep
col_stride   = col_size + h_sep

row_count    = ceil(item_count / columns)
viewport_ext = vertical ? size.y : size.x

first_row = max(0, floor(scroll_offset / row_stride) - buffer_items)
last_row  = min(row_count - 1,
                ceil((scroll_offset + viewport_ext) / row_stride) - 1 + buffer_items)

first = first_row * columns
last  = min(item_count - 1, (last_row + 1) * columns - 1)
```

**条目 i 的主位置**：
```
row = i / columns
col = i % columns
pos(i).main  = row * row_stride
pos(i).cross = col * col_stride
```

### 5.3 增量更新（滚动时）

每帧（或 `scroll_offset` 变化时）：

```
new_range = compute_visible_range()

# 先处理离场
for idx in active_nodes.keys():
    if idx not in new_range:
        unbind_item.emit(active_nodes[idx], idx)
        recycle(active_nodes[idx], get_type(idx))
        active_nodes.erase(idx)

# 再处理入场
for idx in new_range:
    if idx not in active_nodes:
        var type = get_type(idx)
        var node = acquire(type)   # 从池里取或 instantiate
        active_nodes[idx] = node
        position_node(node, idx)
        bind_item.emit(node, idx)
```

**复杂度**：每次滚动 O(k)，k 为新进入 / 离开视口的条目数，通常 ≤ 2~3。

### 5.4 插入 / 删除时的 index 迁移

```
notify_item_inserted(at):
    item_count += 1
    # 所有 index >= at 的 active_node 需要 index + 1
    for (idx, node) in active_nodes reverse iterate:
        if idx >= at:
            active_nodes[idx+1] = node
            active_nodes.erase(idx)
    # 重新计算视口
    update_visible_range()

notify_item_removed(at):
    item_count -= 1
    # 如果 at 在视口内，先 unbind + recycle
    # 然后所有 index > at 的 active_node 需要 index - 1
```

**优化**：批量 notify 时可以合并后再一次性 update。

### 5.5 VARIABLE_SIZE（后续版本）

* 维护 `measured_sizes: HashMap<int, Vector2>`，每次 `bind_item` 后 `NOTIFICATION_SORT_CHILDREN` 测量并缓存
* 未测量的条目用 `estimate_item_size` 占位
* 总高度 = Σ(已测) + (未测数) × estimate
* 滚动到某 index 时，定位误差由"已测前缀和 + 估算"给出；用户滚到时再修正
* 滚动条随着更多条目被测量而逐渐精准（与 Flutter `ListView.builder`、React `react-virtualized` 思路一致）

## 6. 边界情况

### 6.1 焦点与选择

**原则**：焦点 / 选中状态**必须存数据侧**。

* 容器内部维护 `int focused_index = -1`、`HashSet<int> selected_indices`
* 节点被绑定时，容器自动设置节点的 `visual_focus` / `selected` 主题态（通过一个可选接口 `VirtualItemHint`）
* 节点被回收时，如果它当前有 `Control` 焦点，焦点转移到容器本身
* Tab / 方向键导航在容器层面处理，遇到滚出视口自动 `scroll_to_index`

### 6.2 单元内部控件状态

**场景**：单元格里有 `LineEdit`，用户编辑一半滚出视口。

**约定**：

* `unbind_item` 信号被定位为"提交脏状态到数据侧"的时机
* 用户在此处把 `node.line_edit.text` 写回 `data[index]`
* `bind_item` 里重新读出来即可

文档要明确告诉用户这个生命周期，否则必然踩坑。

### 6.3 异步回调中的节点错绑

暴露 `get_bound_index(node)`，用户在异步回调里先判断再操作。见上文示例。

### 6.3.1 `type_provider` 对同一 index 返回值变化

**场景**：某条消息数据修正——从 `SYSTEM_MSG` 变成了 `TEXT_MSG`；或者某个物品从"普通模板"升级为"稀有模板"。用户调用 `refresh_item(i)`。

**默认行为**（容器实现必须覆盖）：

```
refresh_item(i):
    if i not in active_nodes:
        return                                  # 不在视口，下次进入视口时自然用新 type
    var node = active_nodes[i]
    var old_type = _node_type_of(node)          # 内部记 node → type 映射
    var new_type = _resolve_type(i)             # 调 type_provider 重新解析

    if old_type == new_type:
        bind_item.emit(node, i)                 # 原地重绑
    else:
        # 类型变了，必须换节点
        unbind_item.emit(node, i)
        _recycle_to_pool(node, old_type)
        var fresh = _acquire_from_pool(new_type)
        active_nodes[i] = fresh
        bind_item.emit(fresh, i)
        _position_node(fresh, i)
        # 若启用了 animate_layout_changes，这次"换人"走 ENTER/EXIT 预设
        # 否则瞬切
```

**关键点**：
- `refresh_item` 必须查类型是否变化，不能假设"原节点永远能承载新数据"
- 类型变化等价于一次本地 remove + insert，**不**改变 `item_count`、**不**触发全局 index 偏移
- 与 FLIP 集成时，这种换节点属于"同位置换人"，默认用交叉淡入淡出更合理而非滑动，实现上可加一个 `ITEM_TYPE_SWAP_PRESET`（或直接沿用 EXIT→ENTER）

**`notify_item_inserted` / `notify_item_removed` 路径**：插入 / 删除时 `type_provider` 天然按新 index 解析，不存在同一 index 类型变化的歧义，走常规路径即可。

**`notify_items_moved(from, to)` 路径**：若移动前后 type 不同（例如拖拽时分类变了），实现上等价于"to 位置 refresh_item"，复用上述逻辑。

### 6.4 单元内部信号冒泡

**推荐模式**：单元脚本暴露一个轻量信号 `action(name: StringName)`，容器自动转发为 `item_action(index, name)`。

实现上：每次 `bind_item` 时容器自动找子节点里的 `action` 信号并连接（若已连则跳过）；`unbind_item` 不断开（连接在实例生命周期内只做一次）。

备选：用户手动连，但要记得在 `unbind` 里 `disconnect`，心智负担更重。

### 6.5 尺寸变化

* 容器自身 `resized` 触发视口重算
* FIXED_SIZE 下 `item_min_size` 变化触发 `refresh()`
* VARIABLE_SIZE 下，单条 `bind_item` 后的测量结果变化，仅影响后续条目的位置，不立即全量刷新

### 6.6 `item_count = 0`

`refresh()` 清空 `active_nodes`，所有节点回池。滚动条 `max = 0`。视口为空。

### 6.7 池爆满

达到 `pool_size_limit` 后，新入池的节点触发 `queue_free()`。上限足够大时不应频繁 free。

### 6.8 `vertical` 切换

运行时切 `vertical` 属性触发 `refresh()` + 滚动位置归零。与 `BoxContainer` 行为保持一致。

### 6.9 与 Container 布局过渡（FLIP）的集成

`VirtualBoxContainer` 继承 `Container`，自动获得 `animate_layout_changes` 开关。但**子节点集合变化的来源有两类，只有其中一类应当走 FLIP**：

| 触发源 | 是否走 FLIP | 原因 |
|---|---|---|
| 滚动导致的节点回收 / 入场 | **否** | 视觉上用户预期是"滚到别的地方"，不是"物品从 A 位置飞到 B 位置" |
| `refresh()` / `refresh_item(i)` | **否** | 位置不变，只是重绑数据 |
| `notify_item_inserted(i)` | **是** | 真实拓扑变化：后续兄弟节点向后推 |
| `notify_item_removed(i)` | **是** | 真实拓扑变化：后续兄弟节点向前挪 |
| `notify_items_moved(from, to)` | **是** | 真实拓扑变化：跨位置移动 |
| `item_count` 直接赋值 | **否** | 语义等价于 `refresh()`，全量重算 |
| 容器自身 `resized` | **否** | 视口变化不是拓扑变化 |

**实现协议**：

1. `VirtualBoxContainer` 在每次需要排版前，根据**本次 sort 的来源**设置一个内部标志：
    ```cpp
    enum SortSource {
        SORT_SOURCE_SCROLL,           // 滚动 / resize → FLIP 需跳过
        SORT_SOURCE_REFRESH,          // refresh / item_count 赋值 → FLIP 需跳过
        SORT_SOURCE_TOPOLOGY_CHANGE,  // notify_* → FLIP 启用
    };
    SortSource _pending_sort_source = SORT_SOURCE_SCROLL;
    ```
2. 在 `_notification(NOTIFICATION_PRE_SORT_CHILDREN)` 里，根据 `_pending_sort_source` 调用基类的 `skip_next_layout_transition()`（滚动 / refresh 分支）或放行（拓扑变化分支）
3. 每次 `notify_*` 调用时把 `_pending_sort_source = SORT_SOURCE_TOPOLOGY_CHANGE`，然后 `queue_sort()`。下一帧 `_sort_children` 执行完即复位

**批量合并**：同一帧内多次 `notify_*` 只触发一次 `queue_sort`，因此只走一次 FLIP 快照 / 播放——这正是 FLIP 对"批量变更"天然友好的原因，用户不需要额外做 `begin_batch` / `end_batch`。

**入场 / 离场预设**：

- `notify_item_inserted` 路径下，新进入视口的 index 如果在旧视口没出现过→走 Container 的 `ENTER_*` 预设
- `notify_item_removed` 路径下，被移除的 index 如果当前在视口→走 `EXIT_*` 预设，节点由退场区接管，动画完毕后**回池**（而非 `free`，保持池复用）
- 回收路径（滚动触发）下的节点**直接** `remove_child` 回池，**不走** `EXIT_*`

**离场节点回池 vs. free**：这是 VirtualBoxContainer 对 Container 基类行为的定制。基类默认 `apply_exit` 完成后 `queue_free`；VirtualBoxContainer override 这一步改为"回对应 type 的池"。通过基类的 `child_exiting` 信号或覆写虚方法 `_finalize_exit(child)` 实现。

- 默认开关状态：VirtualBoxContainer 的 `animate_layout_changes` 默认值建议保持 `false`（与 Container 一致），用户显式打开即可。但**内部 FLIP 逻辑对来源的过滤始终生效**：即便用户手动把 `animate_layout_changes = true`，滚动回收也不会意外触发 FLIP

## 7. 与现有控件的关系

| 现有控件 | 虚拟化对位 | 关系 |
|---|---|---|
| `BoxContainer` (V/H) | **`VirtualBoxContainer`** | 虚拟化版本，API 心智对齐（`vertical` 同名同义） |
| `GridContainer` | **`VirtualGridContainer`** | 虚拟化版本，`columns` 同名同义 |
| `FlowContainer` | 暂无 | 虚拟化 Flow 布局依赖每项测量前缀和，复杂度高，留待后续 |
| `ItemList` | 不对位 | 自绘文本 / 图标列表，保留；轻量场景继续用它 |
| `Tree` | 暂无（`VirtualTree` 规划中） | 保留；树形虚拟化作为后续提案 |
| `ScrollContainer` | 不继承 | `VirtualBoxContainer` 自管滚动，不是把超大子节点塞 `ScrollContainer` |
| `Container` | **直接继承** | 复用 `Container` 的排版机制与主题路径 |

滚动条：内嵌两个 `VScrollBar` / `HScrollBar`（按 `vertical` 显示一个），与 `ScrollContainer` 行为一致。

**迁移路径**：把一个 `VBoxContainer` 迁移到 `VirtualBoxContainer` 是机械变更：

```diff
- @onready var list: VBoxContainer = $Inventory
+ @onready var list: VirtualBoxContainer = $Inventory

  func refresh():
-     for c in list.get_children():
-         c.queue_free()
-     for item in inventory:
-         var n = SLOT.instantiate()
-         n.set_data(item)
-         list.add_child(n)
+     list.item_count = inventory.size()

+ func _ready():
+     list.item_scene = SLOT
+     list.bind_item.connect(func(n, i): n.set_data(inventory[i]))
```

## 9. 测试策略

### 9.1 单元测试（`tests/scene/test_virtual_box_container.h`）

| 用例 | 要点 |
|---|---|
| 空容器 | `item_count=0` 不应创建任何节点 |
| 少于视口的条目 | 全部实例化，无回收 |
| 大于视口 | 只实例化可见 + buffer |
| 滚动到底 | `scroll_to_index(item_count-1)` 视口定位正确 |
| 垂直 / 水平切换 | `vertical` 切换后视口与滚动条正确切换 |
| 插入 | `active_nodes` 中 `index >= at` 全部 +1 |
| 删除 | 被删条目若在视口需 unbind；后续 index -1 |
| 移动 | from / to 都在视口、只有一侧在视口、都不在视口 |
| 多模板 | 不同 type 节点不混池；类型切换时正确 instantiate |
| 池上限 | 超过 `pool_size_limit` 的节点被 free |
| 异步错绑 | 回调中 `get_bound_index` 返回正确值 |

### 9.2 性能基准

## 10. 风险与未决

| 风险 | 缓解 |
|---|---|
| API 一旦发布难以改动 | 先在用户仓实现原型，收集反馈再提 PR |
| 用户滥用（例如在 `bind_item` 里做重 IO） | 文档明确警告；提供 `item_action` 作为惰性加载触发点 |
| 与未来响应式系统冲突 | 当前 API 是命令式的，响应式层可在其上叠加，不冲突 |
| 可变高度的滚动体验 | 参考 Flutter `ListView.builder` 的成熟做法；初版先不做 |
| 用户误用：小列表强行迁移 | §1.5 决策表 + 文档顶端醒目提示 |

未决：

* `VirtualFlowContainer`（`FlowContainer` 的虚拟化对位）是否纳入 M4+？——依赖每项测量前缀和，工程量大，暂作为未来提案
* 是否增设 `VirtualVBoxContainer` / `VirtualHBoxContainer` 薄壳预设类？——**目前明确不加**，`vertical` 属性足以覆盖；若社区有强烈需求再向后兼容地追加
* 是否提供 C# / GDExtension 友好的基类化接口（而非信号）？——可选，v0.1 先 Signal 路径
