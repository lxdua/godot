# 第 22 章　GC：从引用计数到三色标记

到目前为止 Mini 的内存管理完全靠 C++ 的 `shared_ptr`——简单
直接，但有两个无法绕过的问题：

1. **循环引用泄漏**：`a.next = b; b.prev = a;` 永远不会被释
   放——`shared_ptr` 没有循环检测；
2. **释放抖动**：高频次 push/pop closure / table 时，每次 ref
   ++/-- 都是原子操作（C++ 标准要求），多线程 contention 大；
   单线程里也有 cache miss 成本。

成熟脚本语言（Lua、Python、JavaScript、JVM）都用 **追踪 GC**。
本章我们：

1. 讨论 Mini 这种规模要不要换 GC（结论：教学目的就要）；
2. 实现一个最简单的 **stop-the-world 标记-清扫** GC；
3. 介绍三色不变量与增量 GC 的思路。

## 22.1 引用计数 vs 追踪 GC

| 维度 | 引用计数 (RC) | 追踪 GC |
|------|--------------|---------|
| 实现难度 | 极简 | 中-高 |
| 暂停时间 | 零（或极短，按 dec 链） | 有明显 STW（除非增量/并发） |
| 循环引用 | **无法处理**（需配合追踪 backup） | 天然处理 |
| 多线程 | 原子操作 contention | 单线程 GC 阶段不卡，但要 STW |
| 内存峰值 | 低（即时回收） | 高（堆积到下一轮） |
| 缓存友好 | 释放路径长链 cache miss | 标记阶段访问活对象 |

主流脚本语言的妥协：

* **CPython**：RC 主路径 + 周期 GC backup（专门处理循环）；
* **Lua**：纯追踪 GC（增量三色）；
* **V8 / JVM**：纯追踪 GC（分代 + 并发 + 压缩）；
* **Swift**：纯 RC + 周期不处理（用 weak/unowned 让用户管）。

Mini 教学版我们走 **纯追踪 GC**——一刀切容易讲，且天然处理循
环。

## 22.2 收回所有 shared_ptr

第一步是把堆对象的所有权从 `shared_ptr` 改成"裸指针 + GC 拥
有"：

```cpp
// src/object.h
enum class ObjType { String, Table, Closure, Upvalue, Proto, NativeFn };

struct GCObject {
    ObjType type;
    bool marked = false;
    GCObject* next = nullptr;   // 全局所有对象单链表
};

struct StringObj : GCObject { std::string data; };
struct TableObj  : GCObject { /* keys/values, 内部存 Value */ };
struct ClosureObj: GCObject { ProtoObj* proto; std::vector<UpvalueObj*> upvalues; };
// ...
```

`Value` 改成只持有裸指针：

```cpp
struct Value {
    enum class Tag { Nil, Bool, Int, Float, Obj };
    Tag tag;
    union {
        bool       b;
        std::int64_t i;
        double     d;
        GCObject*  obj;
    };
};
```

把 `std::variant<...>` 替换为 tag + union，省去 RC 开销，但
**所有堆对象的释放责任**全部交给 GC。

## 22.3 GC heap：单链表追踪所有对象

```cpp
// src/gc.h
class GC {
public:
    template <class T, class... Args>
    T* allocate(Args&&... args) {
        T* obj = new T(std::forward<Args>(args)...);
        obj->type = ObjType::ForType<T>();
        obj->next = head_;
        head_ = obj;
        bytes_ += sizeof(T);
        if (bytes_ > next_threshold_) {
            collect();
        }
        return obj;
    }

    void collect();

    void add_root(VM* vm) { vm_ = vm; }

private:
    GCObject* head_ = nullptr;     // 所有活对象的单链表
    std::size_t bytes_ = 0;
    std::size_t next_threshold_ = 1 << 20;  // 1 MB 起步
    VM* vm_ = nullptr;

    void mark();
    void sweep();

    void mark_value(const Value& v);
    void mark_object(GCObject* obj);
};
```

`allocate<T>` 替代了所有 `make_shared<T>`——必须**全代码库统一
通过 GC 分配**，否则有对象漏在追踪链外。

`bytes_ > next_threshold_` 是触发 GC 的条件——分配超过阈值就 collect。
collect 后 `next_threshold_ = bytes_ * 2` 实现自适应（堆稳定时
不会狂 GC，堆涨时阈值同步涨）。

## 22.4 标记阶段：从 root 出发图遍历

**Root 集合**对 Mini 而言：

* `vm_->stack_` 中所有 Value；
* `vm_->frames_` 中所有 Closure 指针；
* `vm_->open_upvalues_` 中所有 Upvalue；
* `vm_->globals_` 里所有 Value；
* compiler 跑到一半时，正在编译的中间产物（如果 compile/run
  是同一进程同一时刻发生，需要小心）。

```cpp
void GC::mark() {
    // 栈
    for (const Value& v : vm_->stack_) mark_value(v);
    // 帧（frame.proto / frame.closure）
    for (const auto& fr : vm_->frames_) {
        mark_object(fr.proto);
        mark_object(fr.closure);
    }
    // open upvalues
    for (auto* uv : vm_->open_upvalues_) mark_object(uv);
    // globals
    for (auto& kv : vm_->globals_->entries()) {
        mark_value(kv.first);
        mark_value(kv.second);
    }
}

void GC::mark_value(const Value& v) {
    if (v.tag == Value::Tag::Obj) mark_object(v.obj);
}

void GC::mark_object(GCObject* obj) {
    if (!obj || obj->marked) return;
    obj->marked = true;

    switch (obj->type) {
        case ObjType::String: break;       // leaf
        case ObjType::Proto: {
            auto p = static_cast<ProtoObj*>(obj);
            for (const Value& c : p->constants) mark_value(c);
            break;
        }
        case ObjType::Closure: {
            auto c = static_cast<ClosureObj*>(obj);
            mark_object(c->proto);
            for (auto* uv : c->upvalues) mark_object(uv);
            break;
        }
        case ObjType::Upvalue: {
            auto u = static_cast<UpvalueObj*>(obj);
            if (u->is_closed) mark_value(u->closed_value);
            // open: 指向栈，栈本身已经被根扫了
            break;
        }
        case ObjType::Table: {
            auto t = static_cast<TableObj*>(obj);
            for (auto& kv : t->entries()) {
                mark_value(kv.first);
                mark_value(kv.second);
            }
            break;
        }
        case ObjType::NativeFn: break;     // 假设只持有 std::function
    }
}
```

DFS 递归——栈深可能爆。生产代码用**显式 worklist**：

```cpp
std::vector<GCObject*> gray;
gray.push_back(root);
while (!gray.empty()) {
    GCObject* o = gray.back(); gray.pop_back();
    // ... 遍历它的引用，把未 marked 的 push 进 gray
}
```

这就是"灰色对象集合"——**三色** GC 概念的来源（白：未访问，
灰：已访问但子节点未处理，黑：自己和子节点都处理完）。

## 22.5 清扫阶段：扫单链表

```cpp
void GC::sweep() {
    GCObject** ptr = &head_;
    while (*ptr) {
        GCObject* obj = *ptr;
        if (obj->marked) {
            obj->marked = false;     // 重置准备下一轮
            ptr = &obj->next;
        } else {
            *ptr = obj->next;
            destroy(obj);
        }
    }
}

void GC::destroy(GCObject* obj) {
    bytes_ -= sizeof_obj(obj);
    switch (obj->type) {
        case ObjType::String:   delete static_cast<StringObj*>(obj); break;
        case ObjType::Table:    delete static_cast<TableObj*>(obj); break;
        // ...
    }
}
```

链表 sweep 的好处：不用维护一个独立"对象列表"，就在 next 链
上直接增删。

## 22.6 测试循环引用

```python
fn make()
    let a = {}
    let b = {}
    a.next = b
    b.prev = a
    return [a, b]
end

for i in range(10000) do
    make()    -- 不保留返回值
end
```

每轮造出两个互相引用的 table 然后丢弃。

* 用 `shared_ptr` 版本：内存持续涨，进程很快 OOM；
* 用 GC 版本：每过 1MB 触发一次 collect，旧 a/b 全部回收，内
  存稳定在阈值附近。

跑 `mini --trace-gc loop.mini` 能看到：

```
[gc] start, bytes=1048576
[gc] marked 12 / 9842 objects
[gc] swept, bytes=4096, next_threshold=8192
```

## 22.7 增量 GC：避免 STW 卡顿

简单标记-清扫的最大问题：堆涨到 100MB 时，一次 collect 可能要
几十毫秒——游戏掉帧、服务器请求超时。

Lua 5.x 的解法是**增量 GC**：把 mark 拆成小步，每次分配几 KB
后跑一小步 mark，最后一步统一 sweep。这样单次 GC 暂停 < 1ms。

但增量 GC 需要**写屏障**（write barrier）：mark 中途用户代码
如果把"白色"对象 a 链接到"黑色"对象 b 上，a 不会被 mark
到——必须在每次 obj 字段写入时插入 barrier 把 a 重新涂灰。

```cpp
// 给 TableObj::set 加 barrier
void TableObj::set(const Value& k, const Value& v) {
    entries_[k] = v;
    if (this->marked /*=黑*/ && v.tag == Value::Tag::Obj && !v.obj->marked) {
        // 三色不变量：黑→白 不允许，把 v 涂灰加进 worklist
        gc().push_gray(v.obj);
    }
}
```

实现起来要在所有写入路径插桩——OP_STORE_LOCAL / SET_INDEX /
STORE_UPVALUE 都要发 barrier。这也是为什么大多教学语言都从"全
量 stop-the-world"起步——理解了再上增量。

## 22.8 分代 GC：再下一步优化

观察：**90% 以上的对象死得非常快**（弱代假设）。每次 full GC
扫遍整个堆白扫了大量长寿对象。

分代方案：堆分 young / old 两个区域，分配走 young，young 满了
做"minor GC"只扫 young；活过几次 minor 的 promote 到 old；
old 区单独"major GC"较少触发。

V8、HotSpot、CoreCLR 都是分代+增量+并发的复合策略。Lua 5.4 引
入了"代际模式"作为可选 GC 策略。

我们 Mini 暂不实现——但你可以试试"young 区是 1MB 的环形 buffer
对象池，old 区是普通链表"，在 Mini 上加分代会让 fib 这类高
速 alloc/free 工作负载提速 2-3 倍。

## 22.9 弱引用与 finalizer

实际 GC 还要解决两个边角：

* **弱引用**：caching 表里的 entry 不希望阻止 value 被回收。
  Lua 用 `__mode = "v"` 元方法标记 weak value；
* **finalizer**：对象被回收前要调一段用户代码（关闭文件、释放
  socket）。GDScript 走 RAII（NotificationPredelete），CPython
  走 `__del__`，Lua 走 `__gc` 元方法。

Mini 教学版可以先不做。如果做：

* 弱引用 = 标记 mark 阶段不 push value 进 worklist，sweep 时
  额外检查弱表里 value 是否已死，是则从表里移除；
* finalizer = sweep 找到一个有 finalizer 的死对象时不立即 free，
  push 进"待 finalize 队列"；专门一轮跑用户代码后再 free。

Lua 的 `__gc` 实现注释长达 200 行，是 Lua GC 最复杂的代码区——
建议初版别做。

## 22.10 实现进度建议

不要一次性铺开。按这个顺序来：

1. **(1 周)** 把所有 `shared_ptr` 替换为 raw `GCObject*`，allocate
   函数集中分配，先漏内存测试（每分配只挂链表，不 collect）；
2. **(3 天)** 写 mark/sweep（DFS 即可），测试一个简单泄漏样本能回
   收；
3. **(2 天)** 改 worklist 替代递归，避免栈爆；
4. **(2 天)** 自适应阈值（`bytes * 2`）；trace 模式打印每次 GC
   的回收量；
5. **(1 周)** 加写屏障 + 增量 mark；
6. （可选）分代 / 弱引用 / finalizer。

实际写下来 Mini 全套 GC 大约 600~900 行 C++，加 50~100 行写屏
障散布在原 VM/Compiler 中。

## 22.11 第 22 章小结

* `shared_ptr` 简单，但不能处理循环引用，且原子开销大——脚本
  语言主流走追踪 GC；
* Mini 替换 `Value` 为 `Tag + union`，所有堆对象继承 `GCObject`，
  由 `GC` 单链表持有；
* mark：从 stack / frames / globals 出发 DFS 染色，非递归用 work-
  list；
* sweep：扫链表，未 marked 的释放，marked 的清掉标记；
* 自适应阈值（`bytes * 2`）平衡内存与 GC 频率；
* 增量 GC 借助三色不变量+写屏障把单次暂停降到 ms 级；分代 GC
  进一步在弱代假设下提速；
* 弱引用、finalizer 是边角但实际项目跑不掉的需求——先做骨架，
  再补这些。

到这里 Mini 的运行时基础已经齐全：词法、语法、字节码、VM、
GC、FFI 一条龙。下一部分是"工程化与生产化"——LSP、REPL 持久
化、错误恢复、跨平台构建，把 Mini 从"教学玩具"推到"能给小
团队用的脚本环境"。
