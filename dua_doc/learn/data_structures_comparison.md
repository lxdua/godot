# 游戏引擎与标准库数据结构对比：STL vs Unreal Engine vs Godot

在游戏引擎开发中，由于对性能、内存布局、跨平台一致性以及编译时间的极致追求，主流商业引擎通常会摒弃 C++ 标准库 (STL)，转而实现一套专门针对游戏开发优化的基础数据结构。本文将对比 C++ STL、Unreal Engine (UE) 和 Godot 中常见数据结构的设计差异。

## 1. 核心设计理念差异

| 特性 | C++ STL | Unreal Engine (UE) | Godot Engine |
| :--- | :--- | :--- | :--- |
| **设计目标** | 通用性、标准化、泛型编程 | 极致性能、内存控制、反射与蓝图集成 | 易用性、快速编译、GDScript/C# 互操作性 |
| **内存分配** | 默认使用全局 `new/delete`，自定义 Allocator 复杂 | 深度集成引擎内存池 (FMalloc)，支持多种分配策略 | 使用引擎自带的 `Memory::alloc`，支持写时复制 (COW) |
| **异常处理** | 深度依赖 C++ 异常 (`std::bad_alloc` 等) | 全局禁用异常，使用 `check()`, `ensure()` 断言 | 禁用异常，使用 `ERR_FAIL_COND` 等宏进行错误处理 |
| **ABI 兼容性** | 依赖编译器实现 (MSVC/GCC/Clang 行为不一) | 引擎内部统一实现，跨平台行为绝对一致 | 引擎内部统一实现，跨平台行为绝对一致 |
| **缓存友好性** | 较差 (如 `std::map` 基于节点) | 极高 (偏好连续内存布局) | 较高 (偏好连续内存布局) |

## 2. 动态数组 (Dynamic Array)

动态数组是最常用的数据结构，要求在内存中连续存储。

*   **STL: `std::vector<T>`**
    *   **底层实现**：通常由三个指针组成：`begin`（指向分配内存的起始位置）、`end`（指向当前有效元素的末尾）、`capacity_end`（指向分配内存的末尾）。
    *   **扩容机制**：当 `end == capacity_end` 时，会申请一块更大的新内存（通常是原大小的 1.5 倍或 2 倍），将旧内存中的元素通过移动构造（或拷贝构造）转移到新内存，然后释放旧内存。
    *   **痛点**：频繁的堆内存分配和元素搬移开销大；无法轻易接管外部已有的内存块；Debug 模式下迭代器安全检查会导致极大的性能下降。

*   **Unreal Engine: `TArray<T>`**
    *   **底层实现**：包含一个指向数据的指针 `Data`，以及两个整数 `ArrayNum`（当前元素个数）和 `ArrayMax`（当前容量）。
    *   **内联分配器 (Inline Allocator)**：这是 `TArray` 的杀手锏。例如 `TArray<T, TInlineAllocator<16>>` 会在对象自身的内存布局（通常是栈上）直接预留 16 个元素的空间。只有当元素超过 16 个时，才会退化为堆分配。这极大地减少了小数组的堆分配开销。
    *   **内存管理**：与 UE 的内存分配器 (FMalloc) 深度集成，支持 Slack（预留空间）的手动管理，避免不必要的扩容。

*   **Godot: `Vector<T>` / `Packed*Array`**
    *   **底层实现**：Godot 的 `Vector<T>` 内部只有一个指针，指向一个堆分配的共享数据块（包含引用计数 `refcount`、大小 `size`、容量 `capacity` 和实际数据）。
    *   **写时复制 (Copy-On-Write, COW)**：当执行 `Vector A = B` 时，并不会拷贝数组内容，而是仅仅将内部数据块的引用计数 +1。只有当 A 或 B 尝试修改数组内容时，才会真正分配新内存并拷贝数据（Detach 操作）。
    *   **优势**：在游戏逻辑中按值传递大型数组时几乎没有开销，非常适合与 GDScript 等脚本语言进行无缝交互。

## 3. 字符串 (String)

*   **STL: `std::string` / `std::wstring`**
    *   **底层实现**：现代 STL 普遍实现了**短字符串优化 (SSO, Short String Optimization)**。内部通常是一个联合体 (Union)：当字符串很短（如小于 15 字节）时，直接存储在对象本身的栈内存中；当字符串较长时，退化为类似 `std::vector` 的堆分配（指针 + 长度 + 容量）。
    *   **痛点**：编码处理混乱（UTF-8, UTF-16 转换复杂）；跨平台宽字符 (`wchar_t`) 长度不一致（Windows 2字节，Linux 4字节）。

*   **Unreal Engine: `FString` / `FName` / `FText`**
    *   **`FString`**：底层直接复用 `TArray<TCHAR>`，是一个动态可变字符串。默认使用 UTF-16 (Windows) 或 UTF-32 (其他平台)。
    *   **`FName`**：**全局字符串池（Name Table）**。底层是一个哈希表，存储了所有出现过的字符串。`FName` 对象本身只包含一个指向该哈希表条目的整数索引（Index）。比较两个 `FName` 是否相等，只需比较两个整数是否相等，速度极快（O(1)），常用于资源路径、骨骼名称等频繁比较的场景。
    *   **`FText`**：包含本地化历史、格式化参数等复杂结构的字符串，专门用于 UI 显示。

*   **Godot: `String` / `StringName`**
    *   **`String`**：底层实现与 `Vector<T>` 类似，同样采用了**写时复制 (COW)** 机制。Godot 4.x 中默认使用 UTF-32 编码（Godot 3.x 为 UTF-8）。
    *   **`StringName`**：���似于 UE 的 `FName`。底层维护了一个全局的 `HashSet`。`StringName` 对象内部只保存一个指向该全局集合中唯一字符串节点的指针。比较时直接进行指针地址比较，速度极快。

## 4. 哈希表/字典 (Hash Map / Dictionary)

哈希表是底层实现差异最大、对性能影响最深的数据结构。

*   **STL: `std::unordered_map<K, V>`**
    *   **底层实现**：C++ 标准强制要求使用**链地址法 (Separate Chaining)**。底层是一个指针数组（Buckets），每个指针指向一个链表。当发生哈希冲突时，新元素会被挂在对应 Bucket 的链表上。
    *   **痛点**：每次插入新元素都需要 `new` 一个链表节点，导致严重的内存碎片；遍历哈希表实际上是在遍历多个不连续的链表节点，**缓存命中率 (Cache Locality) 极差**，对现代 CPU 非常不友好。

*   **Unreal Engine: `TMap<K, V>`**
    *   **底层实现 (基于 `TSparseArray`)**：`TMap` 的核心是 UE 独有的 **`TSparseArray` (稀疏数组)**。`TSparseArray` 本质上是一个连续的动态数组 (`TArray`)，但它允许内部存在“空洞”（被删除的元素）。为了管理这些空洞，它额外维护了一个 **`TBitArray` (位图)** 来标记每个索引位置是否有效，并将所有空闲槽位串联成一个**空闲链表 (Free List)**。
    *   **哈希机制与内存布局**：`TMap` 内部维护了两个主要结构：
        1.  **哈希桶数组 (Hash Buckets)**：一个存储整数索引的连续数组。索引指向 `TSparseArray` 中的位置。
        2.  **元素存储区 (`TSparseArray`)**：存储实际的 `(Key, Value)` 键值对，以及一个 `NextIndex`（用于解决哈希冲突）。
    *   **解决冲突 (内联链表)**：当发生哈希冲突时，`TMap` 依然使用链地址法，但**极其巧妙的是，它的链表节点不是在堆上单独 `new` 出来的，而是直接分配在 `TSparseArray` 的连续内存中**。链表的 `Next` 指针被替换成了 `TSparseArray` 的**整数索引**。
    *   **操作图解**：
        *   **插入**：计算 Key 的哈希值，对桶大小取模得到桶索引。如果桶为空，从 `TSparseArray` 的空闲链表中取出一个槽位放入数据，并将桶索引指向该槽位。如果桶不为空（冲突），同样在 `TSparseArray` 中分配新槽位，并将其 `NextIndex` 指向桶中原有的槽位索引（头插法），然后更新桶索引。
        *   **删除**：找到元素在 `TSparseArray` 中的索引，将其在 `TBitArray` 中标记为无效，并将其加入空闲链表。**不需要释放任何内存**。
    *   **极致的缓存优势**：由于所有元素（包括冲突链表上的元素）都紧凑地排列在一个连续的 `TArray` 内存块中，遍历 `TMap` 实际上就是在遍历一个连续数组（只需跳过 `TBitArray` 标记为无效的槽位）。这使得 CPU 的**空间局部性 (Spatial Locality)** 达到极致，缓存命中率远超 `std::unordered_map`。

*   **Godot: `HashMap<K, V>`**
    *   **底层实现**：使用了**开放寻址法 (Open Addressing)** 结合 **Robin Hood 哈希算法**。底层维护了两个平行的连续数组：一个存储哈希值 (`uint32_t* _hashes`)，另一个存储指向元素的指针 (`HashMapElement** _elements`)。
    *   **哈希机制**：发生冲突时，不使用链表，而是向后寻找空槽位。Robin Hood 策略会在插入时比较“探测距离”（偏离理想位置的距离），“劫富济贫”地交换元素，使得所有元素的平均查找时间趋于稳定。
    *   **取模优化**：使用 **Fastmod** 算法，通过预计算的魔法乘数和位移操作，将缓慢的除法取模 (`hash % capacity`) 替换为极快的乘法，大幅提升寻址性能。
    *   **顺序保证**：为了保证遍历顺序与插入顺序一致（这对脚本语言很重要），`HashMapElement` 内部还额外维护了 `prev` 和 `next` 指针，形成一个双向链表。

## 5. 集合 (Set)

*   **STL: `std::set<T>`**
    *   **底层实现**：通常基于**红黑树 (Red-Black Tree)** 实现。每个节点包含左子节点、右子节点、父节点指针、颜色标志和实际数据。
    *   **痛点**：每次插入都需要在堆上分配节点；树的遍历和重平衡涉及大量的指针跳转，缓存极度不友好；查找时间复杂度为 O(log N)。

*   **Unreal Engine: `TSet<T>`**
    *   **底层实现**：本质上就是一个只有 Key 没有 Value 的 `TMap`。底层同样基于 `TSparseArray` 和哈希索引。
    *   **优势**：查找时间复杂度为 O(1)；内存连续性好。

*   **Godot: `HashSet<T>`**
    *   **底层实现**：与 Godot 的 `HashMap` 完全一致，采用 Robin Hood 开放寻址法和 Fastmod 优化，只是不存储 Value。

## 6. 链表 (Linked List)

*   **STL: `std::list<T>`**
    *   **底层实现**：标准的双向链表。每个节点在堆上独立分配，包含 `prev`, `next` 指针和数据。
    *   **痛点**：内存碎片化严重；遍历时 CPU 缓存几乎每次都会 Miss（缓存未命中），在游戏引擎的核心循环中是性能杀手。

*   **Unreal Engine: 侵入式链表 (Intrusive List)**
    *   **底层实现**：UE 虽然有 `TDoubleLinkedList`，但在底层系统（如物理、渲染队列）中大量使用侵入式链表。**侵入式链表不单独分配节点内存**，而是要求用户在自己的数据结构内部显式定义 `Next` 和 `Prev` 指针。
    *   **优势**：将对象加入链表不需要任何内存分配；对象本身和链表指针在同一块内存中，缓存友好；非常适合管理生命周期由其他系统控制的游戏对象。

*   **Godot: `List<T>`**
    *   **底层实现**：Godot 提供了一个基础的模板双向链表 `List`，节点也是单独分配的。但在核心性能路径（如 SceneTree 的节点管理）上，Godot 同样倾向于使用连续数组 (`Vector`) 或类似侵入式的设计来保证性能。

## 7. 总结

游戏引擎摒弃 STL 并非“重复造轮子”，而是基于特定领域需求的必然选择：

1.  **内存控制**：引擎需要完全掌控内存分配的时机和方式，避免碎片化。
2.  **缓存友好**：现代 CPU 架构下，连续内存（数组）的性能远超基于指针的结构（树、链表）。引擎数据结构极度偏向连续内存布局。
3.  **特定优化**：如 Godot 的 COW 机制、UE 的 `FName` 字符串池、内联分配器等，都是为了解决游戏开发中的特定痛点。
4.  **跨平台与稳定性**：统一的内部实现消除了不同编译器 STL 的行为差异，且通过禁用异常机制保证了软实时系统的性能可预测性。
